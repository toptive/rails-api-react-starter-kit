# Internationalization

`i18n/translations.csv` (`key,en,es`) is the only source for frontend and backend text.
The scripts and initial catalogue come from the Phoenix starter kit. Do not hand-edit
`i18n/locales/*.json` or `config/locales/*.yml`.

```sh
bin/rails i18n:build           # also pnpm i18n:build
```

The builder validates unique nonempty keys and filled cells, runs the shared Node builder,
then creates nested Rails YAML. Flat JSON uses literal dotted keys (`keySeparator: false`).
The YAML builder changes `{{count}}` to `%{count}` for Rails interpolation. Generated YAML
quotes strings so words such as `true` remain strings.

React uses react-i18next. Rails uses `I18n.t("errors.api.not_found")`. Add a CSV key with
English and Spanish together, rebuild, review and stage all generated outputs. `i18n:check`
rebuilds and fails on any difference from the index.

Requests select supported `?locale=` or weighted `Accept-Language` tags; `es-AR` falls back
to `es`, unsupported tags to the next supported tag or English. The around callback uses
`I18n.with_locale`; error rendering explicitly resolves the same locale after rescue. Locale
state never leaks into the next request. Emails use their recipient's locale.

Validation details use stable `validation.*` keys from the CSV. `ApiError` carries the error
code, HTTP status and details; only the controller translates the user-facing message.

## Runtime editing boundary

This skeleton loads baked YAML and JSON. The later translation domain owns runtime admin
edits: synchronize missing reference CSV keys without overwriting admin values, rebuild
catalogues, and reload I18n. `i18n:sync` belongs to that domain; do not simulate it by replacing
runtime edits with a fresh reference CSV.
